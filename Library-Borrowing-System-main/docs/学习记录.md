## 解决的问题
项目中异常散落在各 Service 和 Controller，直接抛给前端，响应格式不统一，且可能泄露内部信息。

## 核心思路
- 用 `@RestControllerAdvice` 拦截所有 Controller 抛出的异常
- 统一包装成项目已有的 `Result<T>` 格式返回
- 分层处理：业务异常 → 参数校验 → 权限异常 → 兜底

## 处理链路

```
Controller 执行
    │
    ▼ 抛出异常
GlobalExceptionHandler 拦截
    │
    ├─ BusinessException          → Result.error(resultCode)
    ├─ MethodArgumentNotValidException → Result.error(400)
    ├─ AccessDeniedException      → Result.error(403)
    └─ Exception (兜底)            → Result.error(500)，不暴露堆栈
```

## 2. DTO/Entity 映射层（Mapper 层）

### 解决的问题
Service 层中内联 DTO 转换逻辑，`convertToDTO()` 方法重复出现，代码冗余且维护成本高。

### 核心思路
- 为每个 Entity 创建独立的 Mapper 类，用静态 `toDTO()` 方法统一转换
- Service 层通过 `XxxMapper.toDTO()` 调用，不再内联转换逻辑

### 创建的文件

| Mapper | Entity → DTO | 作用 |
|--------|-------------|------|
| [UserMapper.java](../server/src/main/java/net/togogo/mapper/UserMapper.java) | `User` → `UserDTO` | 映射 id、username、email、phone、createTime、role |
| [BookMapper.java](../server/src/main/java/net/togogo/mapper/BookMapper.java) | `Book` → `BookDTO` | 映射全部图书字段 |
| [BorrowRecordMapper.java](../server/src/main/java/net/togogo/mapper/BorrowRecordMapper.java) | `BorrowRecord` → `BorrowRecordDTO` | 额外计算 `overdueDays`（逾期天数） |

### 关键点
1. 使用 **静态方法**，无需注入，调用简单
2. 空安全处理：`if (entity == null) return null`
3. BorrowRecordMapper 在转换时附带业务逻辑（计算逾期天数），属于 **含逻辑的映射**
4. Service 层从内联转换改为统一调用后，代码量减少且职责清晰

## 3. 借阅逻辑独立拆分（BookRecordService）

### 解决的问题
`BookService` 中混合了图书管理（CRUD）和借阅管理（借书/还书/续借）两种职责，违反了单一职责原则。

### 核心思路
- 拆出 `BookRecordService` 接口 + `BookRecordServiceImpl` 实现
- 拆出 `BookRecordController` 对应 Controller 层
- 原 `BookService` 只保留图书本身的 CRUD 方法

### 拆出的方法
- `borrowBook()` — 借书（扣减库存、创建借阅记录）
- `returnBook()` — 还书（恢复库存、更新记录状态）
- `renewBook()` — 续借（延长到期日、限制最多续借 2 次）
- `getBorrowRecordsByUser()` — 按用户查询借阅记录
- `getBorrowRecordsByBook()` — 按图书查询借阅记录
- `getOverdueRecords()` — 查逾期记录
- `getAllBorrowRecords()` — 查全部记录

### 关键点
1. 借阅操作是 **事务性** 的：借书需要同时减库存 + 创建记录，用 `@Transactional` 保证原子性
2. 缓存逐出使用 `@CacheEvict(value = {"borrowRecords", "books", "books:all"}, allEntries = true)`，涉及多个缓存区域
3. 续借限制 `renewCount >= 2` 时抛出 `MAX_RENEW_COUNT_EXCEEDED` 异常

## 4. Java 21 升级 + 虚拟线程

### 解决的问题
项目原本使用 Java 17，无法享受到 Java 21 的虚拟线程特性。虚拟线程能大幅降低 IO 密集型场景（数据库查询、Redis 操作）的线程开销。

### 核心思路
- 升级 JDK 版本从 17 → 21（修改 `pom.xml` 的 `<java.version>`）
- Spring Boot 3.2 原生支持虚拟线程，只需一行配置即可开启

### 操作步骤
1. 在父 `pom.xml` 中将 `<java.version>` 从 `17` 改为 `21`
2. 在 `application.yml` 中添加：
   ```yaml
   spring:
     threads:
       virtual:
         enabled: true
   ```

### 原理
- Spring Boot 3.2+ 检测到 `spring.threads.virtual.enabled=true` 后，自动将 `TomcatProtocolHandler` 替换为虚拟线程版本
- 每个 HTTP 请求跑在虚拟线程上（而非操作系统线程），数量可达百万级
- 对于图书管理系统这种 **IO 密集型** 场景（大量数据库查询、缓存操作）提升明显

### 注意事项
- 虚拟线程不适合 **CPU 密集型** 计算（大量计算任务反而会降低性能）
- 不要在虚拟线程中调用 `synchronized` 或 `Thread.sleep()` 阻塞平台线程
- 现有代码无需改动，Spring Boot 自动接管

| 组件 | 文件 | 作用 |
|------|------|------|
| `Result<T>` | [Result.java](../common/src/main/java/net/togogo/common/Result.java) | 统一响应体 `{code, message, data}` |

| `BusinessException` | [BusinessException.java](../common/src/main/java/net/togogo/common/BusinessException.java) | 携带 ResultCode 的业务异常 |


## 关键点
1. 用 `@RestControllerAdvice` 而非 `@RestController`
2. 返回 `Result<T>` 而非 `ResponseEntity`，和项目现有格式一致
3. BusinessException 直接复用 `Result.error(resultCode)`，自动映射状态码和消息
4. 兜底异常不暴露 `ex.getMessage()`，只返回固定的"系统错误"

## 踩坑记录

### 1. 异常处理器顺序陷阱
- `Exception.class` 兜底必须写在最后，否则会覆盖前面的精细化异常（如 `BusinessException`）
- Spring 匹配规则：**精确匹配优先于通用匹配**，不会按方法书写顺序执行，但如果两个异常有继承关系（比如 `NestedException extends BusinessException`且没有专门的处理方法），会被父类处理器吃掉

### 2. 参数校验异常缺少具体字段信息
当前实现只返回 400 状态码：
```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public Result<Void> handleMethodArgumentNotValidException(...) {
    return Result.error(ResultCode.BAD_REQUEST);
}
```
- 前端只知道"请求参数有误"，但不知道哪个字段错了
- 改进方案：从 `e.getBindingResult().getFieldErrors()` 提取字段名和错误消息返回

### 3. 兜底异常没打日志
```java
@ExceptionHandler(Exception.class)
public Result<Void> handleException(Exception e) {
    return Result.error(ResultCode.INTERNAL_ERROR); // ⚠️ 没打日志
}
```
- 生产环境一旦触发兜底，只能看到前端返回了 500，后台没有任何堆栈信息
- 开发期间建议加 `log.error("unexpected error", e)`，否则线上问题无法排查

### 4. @PreAuthorize 权限异常的正确捕获
- `AccessDeniedException` 由 Spring Security 的 `ExceptionTranslationFilter` 抛出
- 如果 Security Filter Chain 在 `@ControllerAdvice` 生效之前就处理了异常，则无法被捕获
- 当前实现中能正常捕获，说明 Filter 顺序没问题，但要注意如果调整了 Security 配置可能需要重新验证

- 使用 Spring Cache + Redis 实现声明式缓存
- 配置 `@Cacheable`、`@CacheEvict` 注解
- 使用 `GenericJackson2JsonRedisSerializer` 序列化

### 配置要点
```java
@Bean
public RedisCacheManager cacheManager(RedisConnectionFactory connectionFactory) {
    // 配置 ObjectMapper，支持 Java 8 时间类型
    // 启用多态序列化，限制可反序列化的类型（安全考虑）
    // 配置缓存过期时间（30分钟）

```

### 使用的缓存区域
| 缓存区域 | 用途 | 过期时间 |
|----------|------|----------|

## 8. 登录防暴力破解

### 解决的问题
账号密码可被暴力破解，安全性低。

### 核心思路
- 使用 Redis 记录登录失败次数
- 连续 5 次失败锁定账号 5 分钟
- 使用原子操作 `increment` 防止并发问题

### 创建的文件
- [LoginAttemptService.java](../server/src/main/java/net/togogo/service/LoginAttemptService.java)

### 关键点
1. Key 格式：`loginAttempt:{username}:{ip}`
2. `isExceeded()` — 检查是否超过最大尝试次数
3. `incrementAttempts()` — 增加失败次数，首次失败时设置过期时间
4. `resetAttempts()` — 登录成功时清除失败记录

## 9. 验证码机制

### 解决的问题
自动脚本可绕过登录限制，暴力破解账号。

### 核心思路
- 使用 `easy-captcha` 生成验证码图片
- Redis 缓存验证码（60秒过期）
- Lua 脚本原子校验验证码，防止并发重复使用

### 验证码流程
```
GET /api/users/captcha
├─ 生成 SpecCaptcha（130x48，4位字符）
├─ 生成 UUID 作为 captchaKey
├─ 缓存到 Redis（60秒）
└─ 返回 { captchaKey, image: base64 }

POST /api/users/login（验证码校验）
├─ Lua 脚本：GET → 比对 → DELETE（原子操作）
├─ 返回 -1=过期, 0=错误, 1=成功
└─ 校验成功后继续登录流程
```

### 关键点
1. Lua 脚本保证原子性：先获取、比对、删除，防止同一个验证码被多次使用
2. 验证码文本转换为小写，忽略大小写差异
3. 清除验证码中的空白字符
4. 前端直接使用 base64 图片，无需额外请求

## 10. 分页参数保护

### 解决的问题
`page`/`size` 参数无限制，可被恶意构造大查询攻击。

### 核心思路
- 在 Controller 层对分页参数进行边界检查
- `page` 限制在 [0, 100]，`size` 限制在 [1, 100]

### 实现方式
```java
page = Math.max(0, Math.min(page, 100));
size = Math.max(1, Math.min(size, 100));
```

### 应用位置
- [BookRecordController.java](../server/src/main/java/net/togogo/controller/BookRecordController.java) — 所有分页接口

### 后续优化方向
- 提取为全局参数校验器
- 使用 `@Max`、`@Min` 注解配合自定义校验器

## 12. 软删除与归档系统

### 学习日期
2026-07-27

### 解决的问题
图书/用户删除为物理删除，数据不可恢复，误删后无法找回。

### 核心思路
- 采用 **归档表模式** 而非传统的 `deleted` 字段标记
- 删除时将数据保存到归档表，再删除原表记录
- 恢复时从归档表读取数据，重新插入原表
- 归档记录保留删除时间和状态，支持追溯和清理

### 创建的文件
- [UserArchive.java](../common/src/main/java/net/togogo/entity/UserArchive.java) — 用户归档实体
- [BookArchive.java](../common/src/main/java/net/togogo/entity/BookArchive.java) — 图书归档实体
- [UserArchiveRepository.java](../server/src/main/java/net/togogo/repository/UserArchiveRepository.java) — 用户归档仓库
- [BookArchiveRepository.java](../server/src/main/java/net/togogo/repository/BookArchiveRepository.java) — 图书归档仓库
- [RecycleBinView.vue](../src/views/RecycleBinView.vue) — 回收站前端页面

### 删除流程
```
删除用户/图书
    ├─ 检查权限（管理员不能删除）
    ├─ 创建归档记录（fromUser/fromBook）
    ├─ 保存归档记录到归档表
    └─ 删除原表记录
```

### 恢复流程
```
恢复用户/图书
    ├─ 从归档表查询记录
    ├─ 删除归档记录（再次删除时可重新归档）
    ├─ 将数据恢复到原表（toUser/toBook）
    └─ 返回恢复后的实体
```

### 清理机制
```
cleanExpired(int retentionDays)
    ├─ 计算阈值时间：当前时间 - retentionDays
    └─ 删除归档表中 deleteTime 早于阈值的记录
```

### 关键点
1. **保留原ID**：归档表使用原表的 ID 作为主键，便于追溯
2. **状态管理**：归档记录删除后即从归档表移除，方便后续再次归档
3. **管理员保护**：管理员账号不能被删除
4. **图书借阅保护**：已被借阅的图书不能删除
5. **缓存失效**：删除/恢复操作后使用 `@CacheEvict` 清除相关缓存
6. **审计兼容**：归档表也标记 `@Audited`，记录归档和恢复操作

### 前端功能
- Tab 切换：已删除图书 / 已删除用户
- 分页浏览：支持分页显示归档记录
- 恢复操作：一键恢复已删除的图书或用户
- 清理过期：清理指定天数前的归档记录（默认30天）

### 踩坑记录
- 归档表的 `id` 字段不能使用 `@GeneratedValue`，需要手动设置
- 恢复时需要注意用户名/ISBN 的唯一性约束（可能与现有记录冲突）
- 恢复后归档记录直接删除，如需保留恢复历史可改为状态标记方式

## 13. API 限流（令牌桶算法）

### 学习日期
2026-07-28

### 解决的问题
接口可被无限调用，有安全风险，易被暴力调用（如暴力破解登录、恶意爬虫等）。

### 核心思路
- 使用 **Token Bucket（令牌桶）** 算法实现限流
- 基于 Redis 实现分布式限流（支持多实例部署）
- 三层限流策略：IP 全局、接口级、用户级

### 创建的文件
- [RateLimitFilter.java](../server/src/main/java/net/togogo/security/RateLimitFilter.java) — 限流过滤器
- [RateLimitProperties.java](../server/src/main/java/net/togogo/config/RateLimitProperties.java) — 限流配置属性
- [TokenBucketService.java](../server/src/main/java/net/togogo/service/TokenBucketService.java) — 令牌桶服务
- [RateLimitException.java](../common/src/main/java/net/togogo/common/RateLimitException.java) — 限流异常

### 令牌桶算法原理
```
令牌桶容量 = capacity
补充速率 = capacity / refillSeconds（每秒补充的令牌数）

请求到达时：
    ├─ 令牌数 > 0 → 消耗1个令牌，允许请求
    └─ 令牌数 = 0 → 拒绝请求（限流）

实现方式（简化版）：
    ├─ 使用 Redis 的 increment 计数
    ├─ 首次请求设置过期时间
    └─ 计数器超过 capacity 时拒绝请求
```

### 三层限流策略

| 层级 | Key 格式 | 默认限制 | 说明 |
|------|----------|----------|------|
| IP 全局 | `token:bucket:ip:{ip}` | 100次/60秒 | 按客户端 IP 限流 |
| 接口级 | `token:bucket:endpoint:{key}:{ip}` | 可配置 | 按接口+IP 限流 |
| 用户级 | `token:bucket:user:{username}` | 200次/60秒 | 按登录用户限流 |

### 特殊接口限流配置

| 接口 | Key | 限制 | 说明 |
|------|-----|------|------|
| 登录 | login | 5次/60秒 | 防止暴力破解 |
| 注册 | register | 10次/3600秒 | 防止恶意注册 |
| 验证码 | captcha | 60次/60秒 | 防止恶意刷验证码 |

### 关键点
1. **继承 OncePerRequestFilter**：确保每个请求只经过一次过滤
2. **过滤器链顺序**：RateLimitFilter 在 UsernamePasswordAuthenticationFilter 之前
3. **IP 获取**：支持 X-Forwarded-For、Proxy-Client-IP、WL-Proxy-Client-IP 等代理头
4. **OPTIONS 请求放行**：CORS 预检请求不经过限流
5. **配置灵活**：通过 `application.yml` 配置限流参数，无需修改代码
6. **异常处理**：RateLimitException 返回 HTTP 429 状态码

### Redis Key 管理
```
Key 格式：token:bucket:{业务key}
过期时间：由 refillSeconds 决定
示例：
    token:bucket:ip:192.168.1.100 → 100次/60秒
    token:bucket:endpoint:login:192.168.1.100 → 5次/60秒
    token:bucket:user:zhangsan → 200次/60秒
```

### 踩坑记录
- 当前实现是简化版计数器，不是真正的令牌桶算法（令牌桶应该平滑补充令牌）
- 更精确的实现需要使用 Lua 脚本保证原子性
- 生产环境建议使用 Bucket4j + Redis 或 Sentinel 实现更完善的限流
- 用户级限流需要认证后才能获取用户名，对未登录用户只能使用 IP 限流

### 后续优化方向
- 使用 Lua 脚本实现真正的令牌桶算法
- 考虑使用滑动窗口算法替代固定窗口
- 添加限流触发告警（如超过阈值时发送通知）
- 结合 Spring Cloud Gateway 实现网关级限流

## 14. 密码管理（修改密码 + 重置密码）

### 学习日期
2026-07-29

### 解决的问题
用户忘记密码或需要定期更新密码时，没有自助修改密码的入口，只能联系管理员处理，缺乏灵活性和安全性。

### 核心思路
- 实现两个密码管理接口：用户自助修改密码 + 管理员重置密码
- 修改密码需要验证原密码，防止账号被盗后被篡改
- 使用 BCrypt 加密存储新密码

### 创建/修改的文件
- [ChangePasswordRequest.java](../common/src/main/java/net/togogo/dto/ChangePasswordRequest.java) — 修改密码请求 DTO
- [ResetPasswordRequest.java](../common/src/main/java/net/togogo/dto/ResetPasswordRequest.java) — 重置密码请求 DTO
- [UserServiceImpl.java](../server/src/main/java/net/togogo/service/impl/UserServiceImpl.java) — 新增 changePassword() 和 resetPassword()
- [UserController.java](../server/src/main/java/net/togogo/controller/UserController.java) — 新增密码管理接口

### 修改密码流程
```
PUT /api/users/password (需登录)
├─ 从 SecurityContext 获取当前用户
├─ 校验新密码与确认密码一致
├─ 校验原密码是否正确（BCrypt 匹配）
├─ 加密新密码并保存
└─ 清除用户缓存
```

### 重置密码流程
```
PUT /api/users/{id}/password (需管理员)
├─ 根据 ID 查询目标用户
├─ 直接加密新密码并保存
└─ 清除用户缓存
```

### 关键点
1. **双重验证**：修改密码时必须验证原密码 + 两次输入一致
2. **权限分离**：用户只能修改自己的密码，管理员可以重置任意用户密码
3. **缓存失效**：修改密码后清除 `users` 缓存，确保数据一致性
4. **事务性**：使用 `@Transactional` 保证密码更新的原子性

### 安全设计
- 原密码校验使用 BCrypt `matches()` 方法，与登录验证逻辑一致
- 新密码通过 `PasswordUtil.encode()` 加密，永不存储明文
- 修改密码接口需要 `isAuthenticated()`，未登录用户无法调用


### 关键点
1. **多类型支持**：getCellStringValue() 处理 STRING、NUMERIC、BOOLEAN、FORMULA 四种单元格类型

## 16. 异步非阻塞编程（Async / N+1 优化）

### 学习日期
2026-07-30

### 解决的问题
1. **批量导入阻塞请求**：Excel 批量导入 500+ 本图书时，同步接口耗时过长，前端需长时间等待，易导致超时
2. **借阅记录查询 N+1**：`getAllBorrowRecords()` 等方法在遍历借阅记录时，每条记录都要单独查 book 和 user，N 条记录产生 2N 次 SQL 查询
3. **大批量写入性能差**：逐条 save 图书数据，无法利用数据库批量插入优化

### 核心思路
- 使用 Spring `@Async` + 自定义线程池实现异步任务
- 使用 Redis 存储任务进度，前端轮询获取状态
- 使用 `TransactionTemplate` 编程式事务管理（解决 `@Async` 与 `@Transactional` 代理冲突）
- 使用 `JdbcTemplate` + 临时表（CREATE TEMPORARY TABLE）实现批量 INSERT ... SELECT
- 批量查询替代 N+1：`findAllById()` 一次性查出所有关联的 book 和 user

### 创建/修改的文件

| 文件 | 操作 | 作用 |
|------|------|------|
| [AsyncConfig.java](../server/src/main/java/net/togogo/config/AsyncConfig.java) | **新建** | 异步线程池配置 |
| [BookServiceImpl.java](../server/src/main/java/net/togogo/service/impl/BookServiceImpl.java) | 修改 | 新增 `batchImportAsync()`、`getImportProgress()`、`batchInsertToTemp()` |
| [BookService.java](../server/src/main/java/net/togogo/service/BookService.java) | 修改 | 新增接口方法 |
| [BookController.java](../server/src/main/java/net/togogo/controller/BookController.java) | 修改 | 新增异步导入接口和进度查询接口 |
| [BookRecordServiceImpl.java](../server/src/main/java/net/togogo/service/impl/BookRecordServiceImpl.java) | 修改 | 新增 `assembleWithBatchQuery()` 消除 N+1 |
| [bookService.js](../src/services/bookService.js) | 修改 | 新增 `batchImportFromExcelAsync()`、`getImportProgress()` |
| [BookManageView.vue](../src/views/BookManageView.vue) | 修改 | 前端异步导入 UI + 进度轮询 |

### 异步线程池配置

```java
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean("asyncExecutor")
    public Executor asyncExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);          // 核心线程数
        executor.setMaxPoolSize(8);           // 最大线程数
        executor.setQueueCapacity(200);       // 等待队列容量
        executor.setThreadNamePrefix("async-import-");
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.setWaitForTasksToCompleteOnShutdown(true);
        executor.setAwaitTerminationSeconds(60);
        return executor;
    }
}
```

### 异步批量导入流程

```
前端提交 Excel
    │
    ▼
POST /api/books/batch-import-async
    ├─ 校验文件格式
    ├─ 生成 taskId (UUID)
    ├─ 将文件转 byte[] 保存
    ├─ 调用 bookService.batchImportAsync(fileBytes, filename, taskId)  ← @Async
    └─ 立即返回 { taskId, message }  ← 不等待导入完成

异步线程中执行：
    ├─ Redis 写入进度："解析中..."
    ├─ BookExcelImporter.parse(is) 解析 Excel
    ├─ Redis 写入进度："解析完成，共 N 条，开始导入..."
    ├─ TransactionTemplate.execute() 编程式事务
    │   ├─ 创建临时表 t_book_temp (LIKE t_book)
    │   ├─ 去掉主键，允许重复 id
    │   ├─ batchInsertToTemp() 批量写入临时表 (每批100条)
    │   ├─ INSERT INTO t_book ... SELECT ... FROM t_book_temp LEFT JOIN 去重
    │   └─ 删除临时表
    ├─ Redis 写入结果："成功导入 N 条"
    └─ 完成

前端轮询进度：
    GET /api/books/batch-import/progress/{taskId}  (每2秒)
    ├─ 查询 Redis 中的进度 key
    └─ 返回当前状态 (解析中 / 开始导入 / 成功导入 / 失败)
```

### N+1 查询优化

**优化前**：每条借阅记录单独查一次 book + 一次 user
```java
// N 条记录 → 2N 次 SQL
for (BorrowRecord record : records) {
    Book book = bookRepository.findById(record.getBookId());      // SQL 1
    User user = userRepository.findById(record.getUserId());     // SQL 2
    // 组装 DTO...
}
```

**优化后**：两次批量查询 + 内存组装
```java
// 收集所有 ID
List<Long> bookIds = records.stream().map(BorrowRecord::getBookId).distinct().collect();
List<Long> userIds = records.stream().map(BorrowRecord::getUserId).distinct().collect();

// 仅 2 次 SQL
Map<Long, Book> bookMap = bookRepository.findAllById(bookIds).stream()
        .collect(Collectors.toMap(Book::getId, b -> b));
Map<Long, User> userMap = userRepository.findAllById(userIds).stream()
        .collect(Collectors.toMap(User::getId, u -> u));

// 内存组装
return records.stream().map(record -> {
    Book book = bookMap.get(record.getBookId());
    User user = userMap.get(record.getUserId());
    return BorrowRecordMapper.toDTO(record, book.getTitle(), book.getAuthor(), user.getUsername());
}).collect(Collectors.toList());
```

### 关键点
1. **`@Async` 与 `@Transactional` 冲突**：异步方法内部事务不生效，改用 `TransactionTemplate` 编程式事务
2. **临时表批量插入**：先批量写入 `t_book_temp`，再通过 `INSERT INTO t_book SELECT ... LEFT JOIN` 实现去重 + 批量插入
3. **`CallerRunsPolicy`**：线程池拒绝策略选择"由调用线程执行"，保证任务不丢失
4. **Redis 进度存储**：进度 key 使用 `import:progress:{taskId}` 格式，设置 10 分钟过期
5. **前端进度条**：根据状态文本匹配进度百分比（20% / 50% / 100%），最多轮询 120 次（约 4 分钟）

### 踩坑记录
- `@Async` 方法必须放在 Spring Bean 中，且通过代理调用（不能直接 `this.batchImportAsync()`），否则异步不生效
- `file.getBytes()` 会将整个文件加载到内存，大文件可能 OOM，生产环境建议用流式处理或分片上传
- 临时表在事务中创建和销毁，事务失败会自动清理，但要确保连接没有被关闭
- `TransactionTemplate.execute()` 内部使用 JdbcTemplate 操作，JdbcTemplate 已配置数据源，可直接使用
- Redis 的 `opsForValue().set(key, value, timeout)` 过期时间单位是 `TimeUnit`，不要忘记设置过期时间

### 后续优化方向
- 大文件分片上传，避免 `getBytes()` 内存占用过大
- 使用 `CompletableFuture` 替代 `@Async`，获得更灵活的异步控制
- 进度百分比改为真正的进度计算（按已处理行数 / 总行数）
- 添加导入结果邮件通知
- 考虑使用 Spring Batch 框架处理大规模数据导入
